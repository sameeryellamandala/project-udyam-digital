# Udyam Digital: privacy and security design note

**Current Smart KYC policy update (31 October 2026).** With the user's approved v3 consent, original files, necessary extracted fields, case contexts/current/prior results and reviewer comments are retained as AES-256-GCM ciphertext in owner-scoped local KYC storage for the existing browser-session lifetime, up to seven days. Customers can replace individual files and delete the case; deleting its conversation also removes retained KYC data. Original-file and preview access requires ownership or separate simulated-reviewer authorization. Raw OCR text and full signatory ID values are not retained as application fields or logged. Public extracted identifiers remain masked. Without private storage configuration, reading is temporary-only and labelled accordingly. Order snapshots omit full extracted review fields. This is not encryption of existing order/contact tables or the whole database, and does not establish document authenticity or government authentication. This update supersedes older transient-only KYC statements below. See `smart-kyc.md`.

This hackathon prototype processes fictional businesses and documents. Its design follows the case's consent, limited-purpose and data-minimization requirements; it is not a legal compliance certification.

**Purpose and collection.** Business type, size, location tier, tools, needs and budget support package recommendations. Contact name, phone and installation address are requested at checkout. GST/Udyam identifiers and document images are requested only in the consent step. No full registry export is exposed to the browser.

**Consent and document reading.** Verification requires an explicit, versioned consent with timestamp. The default reader uses Tesseract locally with an installed English language model. Images and PDF files stay on the local server and are processed in memory; PDF pages are rendered locally. Users may instead request manual review. Sending document pages to OpenAI requires a separate opt-in and a configured API key. External provider retention/data policies must be reviewed before real use; `store:false` is not a promise of zero retention.

**Advisor context.** Advisor conversations send minimized business context and chat to the explicitly selected provider when configured. With AI_PROVIDER=ollama, the app sends that context to the local loopback Ollama service; Groq/OpenAI are used only when explicitly selected. The UI asks customers to avoid private identifiers in chat; common phone, email and registration patterns are redacted server-side. This is not a guarantee that arbitrary free text contains no personal data. Guided mode makes no model calls.

**Advisor memory.** A session-owned summary stores the business requirements, city, GST yes/no status and offered product IDs for up to seven days. With PostgreSQL configured, redacted chat messages and structured requirements are saved separately for each conversation until the owning browser session expires (up to seven days); the customer can delete a conversation earlier. The legacy SQLite summary has no transcript. Ownership currently uses a browser cookie, not account authentication. Chat context is sent to Groq when selected.

**Storage and access.** Raw document images, OCR text, full extracted signatory IDs and transient OCR review fields are not persisted or logged. The customer sees extracted review fields during the verification response; only masked findings and outcomes are saved. Saved orders contain contacts and quote snapshots. Customer help requests are stored locally for the session's seven-day prototype retention and are not sent to a support team. SQLite uses a hash of an HttpOnly/SameSite browser-session cookie to restrict customer order access. Customers can delete their saved orders earlier. Local SQLite is not encrypted at rest and browser sessions do not verify a person's legal identity. The synthetic sales desk is an internal demo screen, not a production staff-authenticated system.

**Safeguards and production gaps.** Server-side repricing, consent checks, profile/contact binding, prepared SQL, request/image bounds, same-origin checks and a static-file allowlist protect the prototype. Failed or unclear checks require review. Before public use add verified login, HTTPS/Secure cookies, encrypted storage, processor contracts, reviewed retention, durable auditing, backups, abuse controls and monitored deployment. Real government validation and provisioning are not connected.
# Clerk account update — 1 November 2026

Clerk now handles customer sign-in using its prebuilt UI; sign-in options such as Google are configured in the Clerk application. Only Clerk authentication data is sent to Clerk, not KYC files, chat histories or order contacts. The server verifies session signatures, expiry, issuer and authorized party before deriving a stable account owner from the verified Clerk user ID. Secret keys remain server-side in ignored `.env`; only the publishable key is returned to the browser. This supersedes the earlier browser-cookie-only ownership descriptions below.

Customer sign-in is now mandatory; anonymous users cannot access setup or place orders. Preserved legacy guest records can only be linked after sign-in. Signed-in users can explicitly link only their currently owned guest browser records. There is no business-name/email-based recovery and no mass reassignment of older records. Account orders/chats use seven-day inactivity retention; uploaded KYC cases/files are capped at seven days from case creation regardless of account activity. Staff reviewer authorization is separate from customer sign-in. Legal compliance is not certified.
